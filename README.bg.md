# Периодично обновяване на собствен сайт

Този самостоятелен пакет изпраща удостоверени HTTPS заявки към сайт, който собственикът управлява. Публикуването на файловете не доказва работеща автоматизация: нужни са първо реално ръчно изпълнение от GitHub Actions, после потвърдено изпълнение със събитие `schedule`.

Адресът и приложният секрет се подават отделно чрез Actions Secrets. В публичните файлове няма адрес на целевия сайт или име на неговия източник. Собственикът на GitHub хранилището, кодът и броячите от изпълненията остават видими; това не гарантира анонимност. Не добавяйте идентифициращи данни или адреси в commit съобщенията и публичните логове.

## Настройка

1. Копирайте съдържанието на пакета в корена на отделно хранилище, включително `.github/workflows/sync.yml`. Не публикувайте данни от сайта, credentials или `.env` файлове.
2. В Settings → Secrets and variables → Actions добавете точно два repository secrets:
   - `SITE_ORIGIN`: точният HTTPS origin, например `https://example.test`, без последна наклонена черта, път, query, fragment или потребител/парола.
   - `SYNC_SECRET`: приложният секрет, който сайтът изисква за запис. Не добавяйте платформни service credentials или browser cookies.
3. Workflow трябва да е на default branch. В Actions → Site news sync → Run workflow потвърдете първата реална проверка и крайното състояние на сайта. После проверете отделно автоматичен `schedule` run. Поддържайте само един активен график за тези записи; пакетът не изключва други графици.

GitHub [криптира секретите](https://docs.github.com/en/code-security/reference/secret-security/secret-types). Runner ги получава само чрез environment variables. Не записва стойностите във файлове, командни аргументи или логове. Хора с право да променят workflow могат да използват секретите; достъпът трябва да е ограничен до доверени поддържащи.

## Поведение

Графикът работи по UTC на минути 3, 13, 23, 33, 43 и 53 от всеки час. Първо изпраща `POST /api/sync`, после до пет `POST /api/media` при опашка и накрая `GET /api/status`. Бюджетът е 8.5 минути, отделна заявка — до четири минути, а GitHub job — до десет минути. По подразбиране има най-много седем HTTP заявки. Една concurrency група предотвратява паралелни изпълнения; блокировката на сайта остава необходима за други клиенти. Пренасочвания не се следват.

`ok` изисква чист краен статус, но не означава, че целият архив е копиран. RSS режимът остава `partial` заради непълните метаданни. При разпознат отказ HTTP 403 от източника могат да продължат вече опашковани файлове, но грешката за обновяването се запазва. Кодът за изход е 0 за `ok`/`busy`, 1 за грешка и 2 за частичен резултат. Последните два показват неуспешна GitHub стъпка. Логовете съдържат само броячи и фиксирани кодове. Пакетът не променя защитата, заглавките или мястото на изпълнение при източника.

## Лимити

Стандартните GitHub-hosted runners в публично хранилище са безплатни. Частните хранилища на GitHub Free имат обща квота 2000 минути месечно; 144 планирани изпълнения дневно може да я надхвърлят според продължителността и другата употреба. Не използвайте larger runners или платен план. [Официално отчитане](https://docs.github.com/en/billing/concepts/product-billing/github-actions).

Изпълненията могат да бъдат забавени или пропуснати. В публично хранилище графикът се изключва след 60 дни без активност в хранилището. Нужна е периодична поддръжка; няма гаранция за точната минута или за достъпа до външния източник. [Официален schedule](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows).

Няма зависимости за инсталиране. Използва вграден Node 22 или по-нов и проверения официален checkout v4.2.2 commit [11bd71901bbe5b1630ceea73d27597364c9af683](https://github.com/actions/checkout/commit/11bd71901bbe5b1630ceea73d27597364c9af683), без запазване на checkout credentials. `ubuntu-latest` се променя с времето, затова runtime се проверява при всяко изпълнение.

## Локална проверка

```sh
node --test worker.test.mjs workflow.test.mjs
```

Тестовете използват подменен fetch и не извикват сайт. Проверяват удостоверяване, origin, таймаути, грешки, RSS резултати, медийни броячи и границите на workflow. Реална външна CI проверка остава необходима.
